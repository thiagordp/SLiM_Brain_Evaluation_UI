# Brain Evaluation UI and Backend Revision Specification

## 1. Objective

Revise the existing Streamlit evaluation system so that it evaluates the current Brain output according to the current Brain schema and skills.

This is not only a visual revision. The new evaluation instrument changes the structure of several responses and therefore requires review of the UI, Brain adapter, persistence model, progress logic, review page, exports, scoring and agreement logic, Google Sheets backend, SQLite backend, and tests.

The implementation should preserve useful parts of the existing architecture where possible. It should not redesign the persistence system from scratch without reason. However, existing structures must be changed wherever they cannot represent the revised evaluation instrument cleanly.

The priority of sources is:

1. Current Brain schema and current relevant skills
2. Decisions recorded in the meeting notes and clarified in this specification
3. Existing evaluation workbook as historical context for the previous evaluation instrument
4. Current Streamlit implementation as an implementation starting point

The current Streamlit interface and its bundled Brain snapshot contain structures from an older Brain schema. They must not determine the semantics of the revised system.

The meeting notes explicitly remove several former fields and evaluations, move Concepts inside Claim evaluation, change Relation evaluation, remove human CITES evaluation, and replace Claim recall with the new completeness scale.  

---

# 2. Language and visual style

The interface should be simple, clean and scientific.

Use concise natural language.

Avoid conversational or LLM-like phrasing.

Avoid rhetorical constructions, unnecessary explanation, decorative wording and excessive punctuation.

Do not expose internal HE criterion identifiers to evaluators.

Do not use code or monospace styling for schema field names or schema values.

Display:

**Claim object**

rather than a code-formatted schema identifier.

Display:

**Temporal reference**

rather than an underscored field name.

Technical IDs such as Claim IDs or Concept IDs may still be displayed when useful for identification, but they should use normal interface typography.

The value being evaluated should appear close to its corresponding question.

Do not place all extracted values in a remote attributes block and ask the evaluation questions elsewhere.

---

# 3. Schema definitions in the interface

For schema-defined fields, place the schema definition immediately below or beside the evaluation question.

Show the complete definition of the field.

For categorical fields, show all possible categories and their definitions, rather than only the definition of the value selected by the Brain.

For example, when evaluating Claim object, show the definitions of Law, Technology and Other.

The current Claim schema defines Claim object, Claim type, Basis, Claim jurisdiction, Legal reference and Temporal reference.

For Claim jurisdiction, do not display an exhaustive list of ISO country codes. Show the complete classification rule, including jurisdiction codes, EU, General and Undetermined.

The schema definitions shown during an evaluation round must be stable. They must not silently change because the repository schema changes after evaluation has begun.

---

# 4. Main evaluation flow

The main navigation should be:

1. Source
2. Claims
3. Datasets
4. Claim recall
5. Review

Concept evaluation belongs inside each Claim.

Relation evaluation belongs inside each Claim.

There is no separate top-level Concept evaluation page.

There is no human CITES evaluation page.

---

# 5. Source

The Source page is informational only.

There are no Source evaluation questions.

Display the complete human-readable Source wiki directly on the page.

The purpose of this page is to give the evaluator enough context to understand the publication before starting Claim evaluation.

Do not require the evaluator to open the Source wiki in a modal.

Do not display a Source completion count.

Do not display Source evaluation controls.

Citation information may remain visible naturally where it already appears in the Source wiki.

Do not add a separate CITES evaluation section or automated-check panel.

The page ends with a clear action to continue to Claims.

The current Source schema contains publication metadata such as title, authors, year, venue, venue type, language, DOI and publication date.

The wiki shown to the evaluator must not present obsolete relation terminology from older Brain versions as if it were current.

---

# 6. Claim navigation

Claims are evaluated one at a time.

Display the current position, for example:

**Claim 3 of 8**

Display the Claim statement prominently.

The Claim page contains four sections:

1. Claim evaluation
2. Schema fields
3. Concepts
4. Relations

Provide Previous Claim and Next Claim controls.

A direct Claim selector may remain available if useful.

All answers must persist when navigating between Claims.

# 7. Claim evaluation

These questions remain separate because they assess different properties of Claim extraction.

## Question 1

**Is this Claim a restatement of another Claim already extracted from this Source?**

Answers:

Yes  
No

If Yes is selected, display a Claim selector.

The selector should contain Claims from the same Source that have already been evaluated.

The evaluator must select the Claim of which the current Claim is a restatement.

Store the selected Claim ID as structured evaluation data.

Do not store the selected Claim only in a comment.

A same-Source restatement is an extraction problem. It must not create a SAME_AS graph edge.

Question 1 has different polarity from most correctness questions: Yes identifies a restatement. Backend logic must not assume globally that Yes means correct.

# 10. Concepts

Concept evaluation always occurs inside the current Claim.

There is no independent Concept evaluation page.

The current schema defines six Concept families:

Legal task

Technical task

Technique class

Normative concern

Interpretation object type

Interpretation canon

Use these six families.

Do not use the older Concept-family structure from the current Streamlit application.

---

# 11. Question 12

**Is this Concept correctly assigned to the Claim?**

Evaluate every Concept currently assigned to the Claim.

Display all assigned Concepts at the same time.

Group them by Concept family.

For each Concept display:

human-readable Concept name

Concept definition

Yes / No radio control

Each Concept has its own independent Yes / No answer.

Selecting an answer for one Concept must not affect another.

Candidate Concepts are also included in Question 12.

If No is selected, a compact comment field may appear under that Concept.

Do not render large comment boxes for every Concept by default.

The current Concept schema defines ID, status, Concept type and definition. It does not define a separate label field.

If the current UI expects a Concept label, derive a human-readable name consistently from the Concept ID or corresponding wiki title. Do not modify the Brain schema merely to support display.

---

# 12. Question 13

**Is this candidate Concept necessary for representing this Claim, given the existing Concept vocabulary?**

Answers:

Yes  
No

Evaluate only Concepts assigned to the current Claim whose status is Candidate.

List all applicable candidate Concepts one below another.

Each candidate receives an independent Yes / No judgment.

A candidate Concept therefore appears in both Question 12 and Question 13.

Question 12 evaluates whether the Concept is correctly assigned to this Claim.

Question 13 evaluates whether the candidate Concept is necessary given the existing vocabulary.

Do not assume that the schema records which Claim originally created the candidate. The current Concept schema records Candidate as a Concept status, not a creator Claim.

If the Claim has no candidate Concepts, do not create an N/A answer. Omit the subsection or show a short informational message.

---

# 13. Question 14

**Are any mapping-relevant Concepts missing from this Claim?**

Question 14 is an interactive Concept browser.

It is not a normal scalar radio question.

---

## 13.1 Eligible Concepts

Before displaying the browser, remove every Concept already assigned to the current Claim.

Assigned Concepts must not appear as possible missing Concepts.

The searchable vocabulary should include the available current Concept vocabulary, including the anchor Concept grid and existing candidate or emergent Concepts where applicable.

The Concept schema defines Anchor, Candidate and Emergent statuses.

---

## 13.2 Search

Display:

**Search Concepts**

The evaluator may type several natural-language words.

Use the search text to filter and rank eligible Concepts.

Search should consider:

human-readable Concept name

Concept ID

Concept definition

Search should be deterministic and local.

It does not require an LLM call.

The exact ranking implementation is an implementation choice, but relevant results should appear before weak matches.

When the search field is empty, show all eligible Concepts.

Results remain grouped by Concept family.

Families without matching results can be hidden during an active search.

---

## 13.3 Persistent selection

Search state and selection state are independent.

Example behavior:

The evaluator searches for Machine learning.

The evaluator selects it.

The evaluator clears the search.

Machine learning remains selected.

The evaluator searches for another Concept.

The evaluator selects it.

Both remain selected.

Changing or clearing the search must never clear the selected Concept set.

---

## 13.4 Selected missing Concepts

Display a separate persistent section:

**Selected missing Concepts**

Every selected Concept appears here as a compact selected item or chip.

Each item shows the Concept name.

Each item has an × control.

Clicking × removes the Concept from the selected set.

Once removed, it becomes eligible in the browser again.

A Concept already selected as missing should not also appear as a selectable search result.

The selected area should be visually distinct from the available Concept list.

Use a restrained visual treatment consistent with the scientific interface.

Do not rely only on color to communicate selection.

---

## 13.5 Explicit no-missing state

An empty list cannot mean both unanswered and no missing Concepts.

Provide an explicit control:

**No additional Concepts are missing**

The backend must distinguish:

Question 14 not yet evaluated

Question 14 evaluated and no Concepts are missing

one or more existing Concepts selected as missing

one or more new Concepts proposed

---

## 13.6 Proposing a new Concept

The evaluator must be able to propose a Concept that does not exist in the current vocabulary.

Provide:

**Propose new Concept**

At minimum collect:

**Proposed Concept name**

**Concept family**

A short explanation may also be collected describing why the existing vocabulary is insufficient.

A proposed Concept should appear in the Selected missing Concepts section.

Clearly identify it as proposed.

Provide an × control so that it can be removed.

Do not directly create or mutate a Brain Concept record.

The evaluation stores the proposal.

Any later creation of a Brain Concept must follow the normal Brain Concept process.

The meeting notes explicitly require the evaluator to be able to add a new Concept after searching.

# 18. Evaluate each Relation only once

The same graph Relation must not be evaluated twice simply because it touches two Claims.

There must be one human evaluation record per graph Relation.

Use a deterministic canonical host for evaluation.

A natural implementation is to evaluate the Relation on the From Claim page and either show it as informational context or omit evaluation controls on the To Claim page.

Another deterministic implementation is acceptable if it guarantees exactly one human judgment per graph Relation.

The Relation's true From and To direction must always be preserved.

# 19. Datasets

Datasets are evaluated one at a time.

Display the current position, for example:

**Dataset 2 of 4**

Display the Dataset name prominently.

Provide:

**Open Dataset wiki**

Open the Dataset wiki in the existing modal over the current evaluation page.

Closing the modal must return to the same Dataset with all entered data preserved.

Provide Previous Dataset and Next Dataset controls.

The Dataset schema defines a Dataset as a dataset, benchmark or corpus on which a Claim rests. A Dataset merely mentioned by a paper does not receive a node.

---

# 20. No Dataset case

If the Source has no Dataset assignment, do not ask Dataset evaluation questions.

Show a concise informational message and allow the evaluator to proceed to Claim recall.

Do not ask a source-level Dataset recall question.

This is an intentional scope decision.

The consequence is that this evaluation instrument does not discover completely missing Dataset nodes when no Dataset was extracted at all.

Do not silently add a Dataset recall question to compensate for this.

# 31. Missing Claims

**Which central Claims are missing from the extracted set?**

Some are represented

Most are represented

Use a multiline text field.

Provide a short instruction asking the evaluator to write each missing Claim as a short proposition and, where possible, indicate the page or section where the Source advances it.

Remove the Source-level Concept completeness question.

There is no HE-20.S or equivalent replacement.

---

# 32. Empty states

Handle empty states deliberately.

If there are no candidate Concepts, Question 13 is absent.

If there are no Relations, no Relation controls are shown.

If there are no Datasets, Dataset evaluation is skipped.

If there are zero extracted Claims, the Source must still be evaluable.

In that case, proceed directly to the later applicable sections and Claim recall.

The evaluator can select None are represented and describe the missing Claims.

Do not create fake N/A answers merely to satisfy the storage model.

---

# 33. Comments

Comments are secondary to structured evaluation.

Do not show large text areas under every question by default.

Recommended behavior:

Question 1: no mandatory comment because the selected restated Claim provides structured correction information.

Questions 2 to 4: reveal a compact comment when No is selected if correction information is useful.

Question 5: show a comment for In part or No.

Questions 6 to 11: show a correction/comment field for No.

Question 12: show a compact comment for No.

Question 13: show a compact comment for No.

Question 14: do not use a normal comment field as the primary response. Existing missing Concepts and proposed Concepts are structured data.

Relations: show a correction/comment field when a judgment is No.

Dataset Description: use the explicit comment rule described above.

Avoid unnecessary evaluator writing.

# 37. Response identity

The existing response identity model must be reviewed because repeated sub-items now exist.

Question 13 needs a distinct judgment for each Claim and candidate Concept pair.

Relation evaluation should use a stable Relation identity and must not depend on which endpoint page happened to render the control.

# 40. Dynamic progress

The revised evaluation contains a dynamic number of applicable items.

The total depends on:

number of Claims

number of Concepts assigned to each Claim

number of candidate Concepts assigned to each Claim

number of unique Relations

number of Datasets

conditional questions and comments

Progress must be generated from the actual applicable evaluation items.

Do not assume a fixed number of questions per Claim or Source.

There is no Source evaluation count.

There is no CITES count.

There is no Dataset recall count.

There is no Source-level Concept completeness count.

---

# 41. Answer semantics

Do not infer correctness globally from literal answer text.

Examples:

Question 1: Yes identifies a restatement.

Questions 6 to 11: Yes means the assigned field is correct.

Question 5 uses Yes, In part and No.

Question 14 is a structured completeness response.

Claim recall uses four ordered categories.

The backend must use criterion-specific semantics.

Review:

global negative-answer constants

numeric score mappings

problem detection

agreement calculations

Review-page highlighting

exports

Do not force every response into the previous universal Yes / In part / No scoring model.

---

# 42. Agreement and scoring

Reanalyse agreement and scoring separately from storage.

Preserve raw evaluation data.

Do not invent numeric mappings for structured responses merely because the previous system expected numeric scores.

Define agreement at the appropriate unit.

Examples:

Question 12 can be compared per Claim–Concept pair.

Question 13 can be compared per Claim–candidate pair.

Question 14 is set-valued and should not automatically be reduced to the old ordinal scale.

Claim recall is ordinal with four levels.

Proposed Concepts and Missing Claims are qualitative data unless a later analysis protocol defines a comparison metric.

If an appropriate agreement metric has not been defined, export the raw structured data rather than inventing one.

# 44. Preallocation

The current Google Sheets design preallocates evaluation rows.

The revised instrument contains dynamic responses, particularly Question 14 and repeated Concept evaluations.

Review whether the existing preallocation strategy can safely support these items.

Do not force dynamic structured responses into brittle fixed rows simply to preserve the old implementation.

Possible solutions include:

extending the normalized response model

introducing structured-response tables

allocating deterministic repeated rows

revising preallocation for dynamic items

Choose the smallest robust solution after inspecting the existing backend.

Preserve:

safe concurrent editing

resume

deterministic lookup

narrow reads where possible

review provenance

exports

# 45. Evaluation specification versioning

Create a new evaluation-specification version for this revised instrument.

Do not reinterpret existing version-3 evaluation rows as answers to the new questions.

Existing evaluations must retain their original meaning and provenance.

Where an old response cannot be migrated semantically, preserve it under its original evaluation specification.

New evaluations use the new specification.

Exports must clearly distinguish evaluation-specification versions.

---

# 46. Freeze the definitions used for an evaluation round

An evaluation study must remain reproducible.

The definitions shown to evaluators should correspond to a known schema/evaluation-specification version and must not silently change during the study.

The Brain Run model records the schema version that was in force when records were written.

The evaluation should retain enough provenance to determine:

which Brain snapshot was evaluated

which evaluation specification was used

which schema definitions were shown to evaluators

Do not silently evaluate structurally incompatible old Brain records against newer field definitions.

# 54. Acceptance criteria

The revision is complete when all of the following are true.

The Source page shows the complete human-readable Source wiki and contains no evaluation questions.

Claims are evaluated one at a time.

Question 1 uses the exact agreed wording and stores the selected restated Claim structurally when applicable.

Questions 2 through 5 use the exact agreed wording.

Questions 6 through 11 use the exact agreed wording.

Schema field questions show the current Brain value and complete schema definition.

Categorical schema definitions show the available categories and meanings.

No schema field or enum is presented in code-style typography.

Removed Claim fields are absent.

Question 12 shows all assigned Concepts grouped by the six current Concept families.

Each Question 12 Concept has its own independent Yes / No judgment.

Question 13 shows only assigned candidate Concepts.

Each Question 13 candidate has its own independent Yes / No judgment.

Question 14 excludes already assigned Concepts.

Question 14 supports free-text Concept search.

Search results remain grouped by Concept family.

Question 14 preserves selected Concepts when the search changes.

Question 14 has a separate Selected missing Concepts area.

Every selected Concept has an × removal control.

Question 14 distinguishes unanswered from explicitly no missing Concepts.

Question 14 allows new Concept proposals.

Proposed Concepts do not directly modify the Brain.

Relations preserve actual From and To direction.

Each Relation is evaluated only once.

Relation Grounding and Relation type are evaluated independently.

Relation Notes remain visible.

Compatible with and In tension with are absent.

Datasets are evaluated one at a time.

The Dataset wiki opens in a modal and does not destroy evaluation state.

No Dataset questions are shown when the Source has no Dataset assignment.

Review contains only current evaluation items.

Structured selections persist across Streamlit reruns and navigation.
