Yes. This page has the right **function**, but I would revise the layout quite a bit.

I checked it against the 7 September meeting again. The intended sequence was explicit: the evaluator should already have read the paper, may inspect the Source wiki, confirms the full paper has been read, and then starts the Source evaluation. The Source wiki remains available again during later evaluation steps.  The meeting also explicitly settled on the idea of judging whether the Brain's output is a **defensible** reconstruction/classification rather than whether the evaluator would personally have coded it identically. The later response scale was agreed as **Yes / In part / No**. 

## 1. The general instructions are good, but I would rewrite them

The current blue text is basically correct, but:

> “under the schema”

is slightly too implementation-oriented for an evaluator.

I would write:

### Evaluation task

> **Assess whether the Brain faithfully represents what the source says. Do not assess whether the paper itself is good, important, persuasive, or legally correct.**

Then immediately underneath, without another large coloured box:

### How to evaluate

> A response should be marked **Yes** when the Brain's representation is defensible under the evaluation criterion, even if another defensible interpretation is possible. Use **In part** when the representation is only partly correct or complete, and explain what is wrong or missing.

I would not mention `No` here because its meaning is obvious, and we will explain the response scale again beside the actual questions.

This preserves the important “defensible” decision from the meeting but makes the prose much simpler.

# 3. Reading confirmation

The checkbox is exactly right and is supported by the meeting: the paper is supposed to have been read **before reaching the evaluation itself**. 

I would use:

Slightly more formal than:

> I have read the full paper...

Then underneath, in small muted text:

# 4. Source wiki

This is where I would make the largest change.

## The current bottom layout is not good

When the wiki opens below the page:

* it significantly increases the page length;
* the evaluator must scroll between the evaluation controls and the wiki;
* it visually looks like part of the evaluation form rather than contextual material;
* the wiki heading duplicates the title already shown above;
* it makes it harder later when the actual evaluation page itself becomes long.

And, as you noticed in the earlier implementation, inspector state can interfere with progression. **Opening contextual information must never block `Start evaluation`, `Next`, `Back`, or any answer control.**

The inspector should be completely independent of evaluation state.

## I would return to the right-side inspector design

This is exactly the use case we discussed earlier.

Closed:

```text
┌──────────────────────────────────────────────────────┐
│ Main paper introduction                              │
│                                                      │
│ W0085 — Explaining Factor Ascription                 │
│ ...                                                  │
│                                                      │
│ [ Open Source wiki ]                                 │
│                                                      │
│ ☑ I confirm that I have read the full paper...       │
│                                                      │
│ [ Start evaluation ]                                 │
└──────────────────────────────────────────────────────┘
```

Open:

```text
┌────────────────────────────────┬─────────────────────┐
│ Main evaluation area           │ Source wiki         │
│                                │                     │
│ W0085 — Explaining...          │ SRC-0004            │
│                                │ Explaining Factor...│
│ Evaluation task                │                     │
│ How to evaluate                │ What the source     │
│                                │ argues              │
│ ☑ I confirm...                 │ ...                 │
│                                │                     │
│ [ Start evaluation ]           │                     │
│                                │     [ minimise ][×] │
└────────────────────────────────┴─────────────────────┘
```

The main evaluation area gets narrower while the inspector is open.

That solves the conceptual problem:

> **evaluation on the left; supporting Brain material on the right.**

# 6. Most important behavioural rule

The inspector is **context only**.

Therefore:

* opening it does not disable anything;
* closing it does not change answers;
* minimising it does not change progress;
* `Start evaluation` works whether the inspector is open or closed;
* later, `Next` and `Back` also work whether it is open or closed.

When `Start evaluation` is pressed, I would automatically close the inspector because the evaluator is moving from the paper-introduction context into the Source-evaluation context.

They can reopen the Source wiki immediately from the next page if needed—the meeting explicitly anticipated this. 

This also follows the context-dependent inspector rule we established earlier.
