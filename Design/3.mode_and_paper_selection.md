Yes. This page is already close to the right structure, but the **state model needs to be made clearer**.

I checked the 7 September meeting again. The important decision was that the evaluator should be able to **save without submitting, leave, return later, and revise any paper already worked on**. The meeting then proposed one additional gate: only after all assigned papers have been completed does the evaluator make a **final submission of the whole set**, after which the answers are locked. This was explicitly motivated by allowing an evaluator to return to an earlier paper and apply a criterion more consistently before final submission. [7 September meeting](sandbox:/mnt/data/Meeting-07-09-Brain.srt)

That matches your clarification now, and it should apply identically to **Training** and **Evaluation**.

## 1. Core behaviour I would fix

For either mode, papers should have only three working states before final submission:

* **Not started**
* **In progress**
* **Complete**

`Complete` does **not** mean submitted. It means:

> I have finished this paper for now, but I may still reopen and change it.

Then there is one state for the whole mode:

* **Final submitted**

Only that final action locks all papers in that mode.

So I would avoid language such as “paper submitted” anywhere before the final batch submission.

The flow is:

```text
Not started
    ↓
In progress
    ↓
Complete
    ↕
can reopen and edit
    ↓

when ALL papers are complete:

Final submission
    ↓
all answers locked
```

The user may evaluate the papers **in any order**.

# Resume behaviour

This should be visible in the card states rather than explained repeatedly.

Suppose Giovanni stops halfway through W0085.

When he returns:

```text
W0085 — Explaining Factor Ascription
In progress
7 of 12 claims completed

[ Continue ]
```

Ideally the app resumes at the **first incomplete point** in that paper.

If W0085 was already marked complete:

```text
Complete
[ Review ]
```

He can reopen it and edit anything.

If an edit makes a required part incomplete again, the paper automatically returns from **Complete → In progress**.

That is important: “Complete” should be calculated from the current state rather than treated as a permanent manual flag.

# Training and Evaluation must use the same component

I strongly agree with this.

There should effectively be **one page implementation**, parameterised by mode.

For Training:

```text
mode = training
papers = W0085, W0206
```

For Evaluation:

```text
mode = evaluation
papers = evaluator's assigned papers
```

Everything else is identical:

* cards;
* states;
* progress;
* Start / Continue / Review;
* autosave;
* any paper order;
* ability to return;
* final batch submission;
* irreversible locking.

This is methodologically better too: training teaches the evaluator the **actual evaluation workflow**, rather than a simplified version.
