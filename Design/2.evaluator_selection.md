## Behaviour

A few precise rules:

* The confirmation button stays disabled until a name is selected.
* Once confirmed, the identity is locked for that browser session.
* Refreshing the page should preserve the selected evaluator where possible.
* The evaluator should not see a normal **“Change evaluator”** button afterward.
* If someone genuinely chooses the wrong identity, the clean solution is to end/restart the session rather than expose an easy identity switch inside the evaluation workflow.
* The selected name is what should be written into all later review/response records.

## One thing I would *not* show

I would not show:

> Group A
> Group B
> Group C

on this screen.

The current assignment email has a naming collision between the **groups** and the **AGR split names**. Those labels matter internally, but they add no value to the evaluator.

The evaluator only needs:

> **Who am I? Which sets are mine?**

So I would use names + `AGR-X` / `IND-X`, and let the application handle pair membership internally.

## Overall assessment of the current screenshot

The logic is good. I would change three things:

* make the content **narrower and visually centred**, consistent with the revised password screen;
* replace **“Who is evaluating?”** with **“Select evaluator”**;
* after selection, show the evaluator's **assigned split IDs before confirmation**, because selecting the wrong name has real consequences for both paper loading and attribution of results.

This page can then be considered quite stable.
